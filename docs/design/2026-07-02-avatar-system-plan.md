## v1 → v2 변경 요약 (3줄)

1. **런타임 교체 안 함 (신설 D0).** v1의 R3F 실시간 3D는 "지금"이 아니라 **트리거 3개** 달성 시의 다음 스테이지. 지금은 **3D 에셋 파이프라인 + 2D 베이크 + 기존 PixiJS 월드**.
2. **규모 전제 하향.** "수백~수천" → **50명 설계 / 100명 검증** (실수요 = 팀 3~4개 × 6~10명). 수천 명 엔지니어링은 YAGNI로 이동.
3. **본선 추월 금지 게이트.** Phase 1 진입 전 **작업 레이어 첫 슬라이스**(지시→2에이전트→artifact)가 존재해야 함. Phase 0a는 Frozen-전시 안무 MVP와 통합(1석2조).

## 0. 북극성

**"살아있는 AI 사회"를 만든다. 아바타는 그 사회의 *언어*이지 주인공이 아니다.**
→ 최고의 캐릭터가 아니라 **확장 가능한 아바타 시스템**을 만든다.

단, 이 트랙은 **보조선**이다 — 본선은 작업 레이어(실제 에이전트 사건의 시각화). 아바타 트랙이 본선을 추월하지 않도록 게이트(§5)로 강제한다.

## 1. 다섯 가지 지침

1. **행동 우선.** 로우폴리라도 걷고·바라보고·타이핑하면 산다. 정적 고화질 모델은 죽어 있다.
2. **프레임워크는 지금, 에셋은 나중.** 리그·소켓·베이크 규격은 지금 확정. 대량생산은 규격 검증 후.
3. **2-티어 분리.** 화려한 2D = 카드/초상(지금 마음껏). 월드 = 로우폴리 소스→베이크(단순·확장). 단 LED 모양·후드색·키컬러 2~3개는 공유해 정체성 연결.
4. **아바타 = 데이터.** 캐릭터는 손으로 만든 모델이 아니라 매니페스트 JSON의 한 행. **매니페스트 1행 = 베이크 1회 = 새 에이전트.**
5. **성능 예산이 아트 예산을 규정.** 현 스택에서 성능 예산 = **베이크 용량/로딩 예산** (프레임셋 크기 상한 + 캐스팅된 에이전트만 lazy-load).

## 3. 아바타 시스템 구조 (v2)

```
베이스 로봇 1개 (공통 메시 + 휴머노이드 리그, GLB)
        │
        ├─ 소품(모자·마이크·태블릿…): 본 소켓에 강체 부착   ← Blender(MCP 자동화)에서 조립
        ├─ 코스튬: 초기엔 바디 통스왑
        │
        ▼
   베이크 파이프라인 (tools/avatar-render 확장)
   매니페스트 1행 → 4방향 × 애니 프레임 PNG → AVATAR_REGISTRY 등록
        │
        ▼
   PixiJS 월드 (기존 IsoCharacter/SpeechBubble/이름칩 그대로)
        ├─ 색/팀컬러: 중립색으로 베이크 + PIXI tint  ← 재베이크 없이 색 변형 ★
        └─ 얼굴 스크린: 머리 위 오버레이 스프라이트 교체 ← 재베이크 없이 표정 무한 ★
```

**핵심 우위 = 얼굴이 '스크린'이라는 점 — 2D에서 오히려 더 강력.** 페이셜 리깅을 통째로 우회할 뿐 아니라, 표정·상태 LED가 몸 베이크와 독립된 작은 스프라이트라 조합이 공짜다.

### 표정 vs 소품 — 무엇을 굽고 무엇을 겹치나 (2026-07-03 확정)

| | 방식 | 이유 |
|---|---|---|
| **표정 (LED 눈)** | **런타임 오버레이** — 빈 검은 바이저로 몸을 굽고, 표정은 바이저 위 절차적 PIXI 도형(링·하트·게이지·$·깜빡임…)으로 실시간 교체 | 감정선 무한·재베이크 0·비용 0. 상태 신호(`activeState`/typing/thinking/activity)가 이미 배선돼 있어 "이동=기본, 대화/생각/유휴=표정 변화"가 즉시 가능. sw/se만 표시(뒷면 숨김), 방향별 고정 앵커(치비라 머리 이동 미미; 필요 시 픽셀 측정기로 위상별 오프셋 자동 추출) |
| **역할 소품 (태블릿·마이크…)** | **베이크 타임 소켓 부착**(D3) 후 몸과 함께 굽기 — 매니페스트 `{propL, propR}` | 거의 안 바뀌는 정체성 요소. 걷기 애니의 손 움직임을 공짜로 완벽 추적 |
| 일시적 아이템 | (선택) 정지 상태 한정 런타임 오버레이 | 걷는 중 손 추적 오버레이는 2D에서 비용 대비 낮음 |

**전제:** 표정 시스템용 베이스 모델은 **빈 검은 스크린 얼굴로 생성**해야 함(눈이 텍스처에 구워지면 오버레이와 충돌). → C-1 입력 규칙에 추가. 현 `robot-analyst`(링 안경 눈 구움)는 고정-표정 아바타로 사용, 표정 시스템은 다음 세대부터.

## 5. 로드맵

### Phase 0 — 두 미지수 싸게 제거 (병렬, **0a 먼저**)
- **0a. IdleChoreographer MVP** *(v1의 "행동 회색박스"를 기존 Pixi 월드로 재정의 — 부록 A의 Frozen-전시 아키텍처 검증 겸용)*

  - 6명 × 10분 결정론적 스케줄(절대시간 슬롯→pose 직접 계산), 손으로 고른 waypoint 6~10개(**비계일 뿐** — 최종형은 walkable 그래프 전체, 맵 확장 호환), 정적 JSON activity 말풍선
  - `VisualAgent` 어댑터로 기존 IsoCharacter/SpeechBubble 재사용, 상호작용 버튼은 Frozen에서 "Live 시작"으로 분리
  - *완료 기준:* ① 30분 열어둬도 Convex I/O 사실상 무증가 ② 멀티탭/새로고침에서 같은 시각=같은 배치 ③ "살아있는 것처럼 보이나" 눈 판정
- **0b. 파이프라인 스파이크** — 로봇 1개(Tripo Game Ready) → AccuRIG → Mixamo 애니 5종 → GLB
  - *완료 기준(관문):* 자동리깅 메시가 관절 안 뭉개고 깨끗이 움직인다 **+ 우리 베이크 파이프라인에서 4방향 프레임이 깨끗하게 나온다.** 깨지면 → 리토폴로지/외주 결정.

### 🚧 게이트 — Phase 1 진입 조건
**작업 레이어 첫 슬라이스(지시→2에이전트→artifact→아바타 연기)가 존재할 것.** 아바타 트랙은 병렬 보조선이며 본선(작업 레이어)을 추월하지 않는다.

### Phase 1 — 표준 확정 + 소켓/베이크 실증
- D1~D5 확정 문서화.
- **소켓 스파이크:** 모자가 걷기 애니 중 머리 본을 찢김·부양 없이 추종 (베이크 결과 기준으로 판정).
- **베이크 예산 측정:** 변형 10종 × 애니 N종 베이크 → 용량·베이크 시간·lazy-load 체감 측정 → D4 숫자 확정.
  - *완료 기준:* 매니페스트 10행이 예산 안에서 깨끗하게 굽힌다.

### Phase 2 — 모듈 변형 시스템 (데이터 주도, 소량 먼저)
- `avatar_manifest.json` 구현 → 매니페스트로 베이크 조립.
- 손/반자동 6~10종 + 클리핑 QA → 깨끗해진 뒤에야 Blender MCP 배치 생성.
- 2D 카드 병렬 생성 (키컬러·LED 공유).
  - *완료 기준:* 매니페스트 한 줄 추가 = 새 에이전트 등장.

### Phase 3 — 행동 심화 + 피델리티 점진 상향
- 안무 확장(walkable 그래프 전역 이동·조우 스킷·일과표·희귀 이벤트) + 작업 레이어 사건 연기 통합.
- **주의:** "실제 제품" = 작업 레이어 시각화. 행동 심화는 그 무대 위 연출임.

## 부록 A — Frozen-전시 안무 아키텍처 (2026-07-02, Claude 제안 + Codex 교차검증 합의)

**문제:** 유휴 전시에 서버 엔진(1초 틱 saveWorldStep × 구독 탭)을 돌리는 것 자체가 구조적 비용 — LLM을 다 꺼도 DB I/O 시간당 수백 MB (7월 쿼터 1.5일 만에 초과의 원인).

**합의 구조:**
```
[유휴 모드 = 기본]  월드 Frozen(stoppedByDeveloper) · worldState 구독/heartbeat 차단
   └ 클라이언트 안무: 절대시간 슬롯 기반 결정론(멀티탭 동일), walkable 그래프 위에서만,
     대사는 repo 정적 JSON(페르소나 풀·조우 스킷·일과표·희귀 이벤트, 선택적 심야 nano 배치 보충)
[실사건 모드]  작업 레이어 이벤트를 별도 소형 스트림으로 구독 → 서버 타임스탬프+duration 기준 연기
[풀 엔진 모드]  사람 참여 시에만 unfreeze ("Live 시작" 버튼) — usage guard 5분 컷
```

**Codex가 잡아준 함정 (설계에 반영됨):**
1. 구독을 안 끊으면 안무를 얹어도 I/O 절감 없음 — `useServerGame`(serverGame.ts)·`Game.tsx`가 이중 구독 중, 이 절단이 구현의 본질
2. heartbeat는 `inactive` 월드를 자동 재기동함(world.ts) — 전시 탭은 heartbeat 발신 금지, 안전한 정지는 `stoppedByDeveloper`
3. 시드+프레임 적분은 탭 스로틀링/FPS/float로 어긋남 — 절대시간 슬롯에서 pose 직접 계산
4. 서버 상태와 가짜 상태 혼입 금지 — `VisualAgent` 별도 프레젠테이션 모델
5. 실사건 전환은 수신시각이 아닌 서버 타임스탬프 기준
6. 이동은 walkable waypoint 그래프 위에서만 (충돌·occlusion 품질 = 제품 신뢰)
7. 검증 지표: Frozen 30분 → I/O 무증가 + 멀티탭 동일 배치

**LLM 대화의 위치 (오해 방지):** 실 API 대화는 삭제가 아니라 **기본값 변경** — Live 모드에 보존(옵트인), 그리고 의미 있는 형태로는 작업 레이어(에이전트 실통신)로 승격. 캔드 잡담은 실작업 내용을 흉내 내지 않는다(07-01 정직함 경계).

**팀 확장 방향 (같은 날 합의):** 한 세계, **팀 = 떠 있는 플랫폼(섬)** 추가 방식(네오트라 덱·마케팅 아일랜드·유튜브 스튜디오…). 세계관 교체는 코스메틱 축으로 별개 유지. 분리 재검토 트리거 = 한 화면 가독 실패 or 팀별 상이한 관객.

## 부록 C — Phase 0b 스파이크 레슨 (2026-07-02/03 실전, 시행착오 전부)

> **결과: 관문 통과.** 이미지 → Tripo(생성·리깅·걷기) → 우리 베이크 → 게임에서 4방향 보행까지 end-to-end 검증 (`robot-analyst`, Lyra로 캐스팅). 아래는 다음 번을 위한 전체 시행착오 기록.

### C-1. 소스 쪽 (Tripo 워크플로우 — 첫 사용 레슨)

1. **입력 이미지에 바닥 그림자가 있으면 발밑 원판이 같이 모델링된다.** ★ 오늘의 최대 함정. 입력은 **순수/투명 배경 + 캐릭터만 부유** 상태로. 이미 생긴 원판은 Tripo **Segment**로 파트 분리→삭제.
2. **라이팅 규칙: "강한 반사·그림자 금지, 부드러운 확산광 유지"** (Tripo 공식 가이드로 교정, 2026-07-03). 금지 = 하드 스펙큘러/글레어·blown highlight·강한 림라이트·하드 그림자 — AI가 글레어를 지오메트리 변형으로 오해하고 하이라이트/그림자를 텍스처에 얼룩으로 구움. 유지 = 부드럽고 고른 확산광 — **셰이딩은 형태·재질(유광 바이저의 PBR 광택 추론) 인식에 필요**하므로 완전 무광 플랫은 오히려 해로움. 프롬프트 상용구: *"plain background, no ground shadow, soft even diffuse studio lighting, no harsh speculars or blown highlights"*. **표정 시스템 대상 모델은 얼굴을 "blank black visor screen, no facial features"로** (눈이 구워지면 런타임 표정 오버레이와 충돌 — §3 표정 표 참조).
3. **베이스 캐릭터는 빈손 A-포즈로.** 손에 든 소품(태블릿·펜)은 소켓(D3)으로 나중에 부착. (이번엔 운 좋게 Tripo가 소품을 스스로 떨궜음.)
4. **멀티뷰(턴어라운드)는 "같은 포즈·같은 소품·같은 표정 + 같은 키(스케일)"**여야 함. 정면·후면·좌우의 **캐릭터 키가 동일**해야 뷰 간 정합이 맞음 — 프롬프트에 "consistent height across views" 명시하거나 생성 후 키를 맞춰 크롭. 오늘 3뷰는 포즈/소품이 제각각 → 사실상 정면 1장 생성이 됐는데도 뒷면 품질은 합격이었음 (정면 1장으로도 스파이크는 충분).
5. **Tripo 산출물은 3단계가 서로 다른 파일**: ① 메시만 → ② 리깅됨(스켈레톤 41본, 클립 없음) → ③ **애니 포함**. 게임에 필요한 건 ③. Export 시 애니메이션 포함 여부 확인 (우리는 ①→②→③ 세 번 받았음).
6. **애니 클립 이름은 제멋대로**(`NlaTrack`) — 우리 render.html이 walk 매칭 실패 시 첫 클립으로 폴백하므로 OK.
7. **걷기 클립은 여러 걸음이 들어 있다** (2.375s ≈ 4걸음). 아래 C-2의 WALK_LEN 규칙과 직결. 팔 스윙이 있는 걷기 프리셋인지도 뷰어에서 확인.
8. **라이선스/크레딧**: HD 생성 55크레딧 소모. Privacy 기본 "Sharing Only" — 상용 전 반드시 플랜 조건 확인(D6).
9. Tripo 리그는 **ActorCore/AccuRIG 표준 네이밍 41본** — 깨끗함. 필요 시 다른 휴머노이드 애니 재타게팅 가능. (Mixamo/AccuRIG 폴백은 이번에 불필요했음 → 툴체인은 "Tripo 단독 우선"으로 단순화 가능.)

### C-2. 파이프라인 쪽 (베이크 — render.html에 코드로 박힌 레슨)

1. **크기 정규화는 "보이는 메시" 기준** — `Box3.setFromObject`는 본/엠티 extent까지 재서 폭발(RobotExpressive: 메시 5u vs 뼈대 149u → 점 크기로 축소). 가시 메시 union으로 측정, `TARGET_HEIGHT=0.671`(켄니 male-a)로 정규화 → 어떤 소스든 켄니와 동일 프레이밍, 기존 12아바타 재베이크는 무변화.
2. **root motion 제거** — Tripo/Mixamo 걷기는 전진 이동 포함 → 4위상 샘플마다 위치가 밀려 인게임 들쭉날쭉. 매 프레임 제자리 재중심화로 in-place 사이클화.
3. **센터링은 몸통 뼈(Pelvis) 기준, x/z 양축** — ① 메시 AABB 중심은 안테나/팔이 방향별로 밀어서 프레임 밖 잘림+흔들림, ② 화면 가로축만 보정하면 기울어진 오소 카메라에서 **깊이 오프셋이 화면 세로를 밀어** 방향별로 가라앉음(ne/nw sink). 뼈를 월드 수직축(x=z=0)에 고정 = 중앙 정렬 + 깊이 고정 동시 해결.
4. **`WALK_LEN` = 한 보행 주기(클립 전체 아님)** — 전체 클립(4걸음)을 4프레임에 압축하면 스트라이드가 앨리어싱돼 포고 점프처럼 재생. 클립길이 ÷ 걸음쌍 수 (이번: 2.375/2=1.1875). 베이크 후 4프레임에서 다리가 교차하는지 눈검증.
5. **`YAW_OFFSET`은 모델마다 다르다** — 켄니 -45, 이 로봇 **-135**. 캘리브레이션: sw 프레임이 "정면-좌하단"을 보면 정답 (켄니와 사분면 비교). 오늘 -90→-45→-135 삼세번.
6. **검증 루틴**: 중심선(50%)+발앵커선(88%) 가이드 몽타주로 4방향×위상 확인 → 인게임은 Playwright. 이 루틴이 세 버그를 전부 픽셀로 잡아냈음.

## 부록 D — 렌더 부하 실측 (2026-07-03)

**질문:** ① 애니를 리치하게 하면 시스템 부하가 얼마나? ② 프레젠테이션을 서버에서 돌릴 필요가 있나?
**방법:** 현재 앱(6~7 아바타·걷기·앰비언트 FX 전부 켜짐)에서 Playwright로 FPS·JS힙 실측 + 텍스처 VRAM은 프레임 치수로 해석 계산 + 디스크는 실측.

### 실측 (지금)
| 지표 | 값 |
|---|---|
| FPS | **76** (스로틀 없음) |
| JS 힙 | **37MB** used / 83MB total (앱 전체) |
| VRAM(추정) | **~70MB** (7룩 × 20프레임 × 0.5MB) |
| 디스크 | 룩당 **~939KB**(걷기 1개·20프레임·47KB/프레임), iso-slice 전체 13MB |
| 캔버스 | 2400×2296 (retina), maxTexture 16384 |

**결론: CPU/GPU 렌더는 놀고 있음.** 스프라이트 교체는 GPU에 공짜라 에이전트 수(6→50)는 렌더 부담이 아님(PIXI 배칭).

### 스케일 법칙
```
VRAM ≈ (고유 아바타 룩 수) × (프레임/룩) × 0.5MB   # 256×512 RGBA, 압축 없음
CPU  ≈ 상수 (에이전트 수·애니 다양성에 둔감; 룩 공유 시 텍스처도 공유)
```
부하는 **"에이전트 수"가 아니라 "고유 룩 × 애니 다양성 × 프레임 크기"** 로 늘어남. PNG는 디스크에선 47KB지만 GPU에선 256×512×4=**0.5MB/프레임**으로 팽창(≈10배)이 핵심.

### 외삽
| 시나리오 | 고유 룩 | 애니 | 프레임/룩 | VRAM |
|---|---|---|---|---|
| 지금 | 7 | 1 | 20 | ~70MB ✅ |
| 리치, 순진하게 | 50 | 8 | ~132 | ~3.3GB ⚠️ |
| 리치 + 룩 공유(50에이전트→12룩) | 12 | 8 | ~132 | ~800MB |
| + 애니 lazy-load(안 쓰는 애니 미로드) | 12 | ~3활성 | ~50 | ~300MB |
| + 프레임 192²(256²→) | 12 | ~3 | ~50 | **~175MB** ✅ |

### 답
1. **애니 리치화 = OK.** 현실 규모(룩 ≤12·에이전트 수십)에선 기본 위생(룩 공유 + 애니 lazy-load + 프레임 ≤256²)만 지키면 VRAM 수백MB — 노트북도 여유. 3GB 폭발은 "50 고유 룩 × 8 풀애니 × 큰 프레임 전부 선로드"라는 안 할 짓 한정.
